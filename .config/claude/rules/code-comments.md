# コメントとコミットメッセージの書き分け

情報の置き場所を次で使い分けること:

- **コードコメント**: コードから読み取れない制約・不変条件のみ (例: 「この API は分/時フィールドを無視する」)。
  原則 1〜3 行以内。以下はコメントに書かない:
  - WHAT (コードを読めば分かること)。例:「// ユーザー ID を取得する」「// ループを回す」。動作は名前とコードで示す
  - 次の行が何をするかの言い換え
  - 変更の履歴・経緯・理由 (「〜を追加した」「旧実装では〜だった」「元は〜」「〜のために」「〜だったので修正」「〜を防ぐため」) → コミットメッセージへ
  - レビュアー向けの説明 (「この変更で〜が直る」「従来は〜だった」) → PR 本文へ
  - 廃止済みの仕組みへの言及 (「X は使わない」「X からの移行」)。現在の仕様だけを書く
  - タスク ID / Issue / PR 番号への参照 (「(UZU-XXXX)」「#123」等。git blame で辿れる)

  良い例: 「job 内のどのステップで失敗しても (バリデーション/認証/dispatch 呼び出し) ここで拾う。」
  （経緯や理由を含めず、コードから読み取れない制約だけを 1 文で書いている）

  悪い例 (Terraform): 「# Zoom と Google の検証値を統合」
  （何が入っているか＝コードを見れば分かる内容 + なぜ統合したかの経緯になっている）
  良い例 (Terraform): 「# apex の TXT 値は全てこの 1 リソースに列挙する (Route53 は name+type ごとに 1 レコードセットしか持てない)」
  （集約した経緯ではなく、コードから読み取れない Route53 の制約だけを書いている）
- **コミットメッセージ**: 変更の why (なぜこの変更が必要だったか、どんな問題があったか、なぜこの方法を選んだか)
- **PR 本文**: レビュアー向けの背景・設計判断・動作確認結果・スクリーンショット
